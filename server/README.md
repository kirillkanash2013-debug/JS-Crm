# JS Control: автономный сервер, прототип 0.6.0

Сбор выполняет серверный Chromium. Пользовательский браузер после подключения не нужен. Cloudflare Worker из `worker/` остаётся шлюзом Telegram; этот сервис разворачивается отдельно на Linux-сервере с Docker. Продакшен CRM и Dolphin не меняются.

## Что реализовано

- HTTPS API через Caddy, персональные ключи клиентов, отдельные подключения и результаты.
- AES-256-GCM: сессии, прокси, задания и результаты зашифрованы на диске. Ключ шифрования хранится отдельно в `.env`.
- Передача Facebook cookies, токена, User-Agent и необязательного прокси из расширения с отдельным согласием. Поддерживаются публичные IPv4 HTTP/SOCKS5 прокси; DNS фиксируется при подключении, внутренние адреса отклоняются. Только cookies Facebook; проверяется совпадение c_user и выбранного соца.
- Сервер проверяет владельца в Ads Manager и через `/me`, читает все доступные кабинеты, кампании, группы, объявления и campaign spend по дням.
- Очередь переживает перезапуск. Незавершённый сбор запускается повторно. При ошибке предыдущий полный результат сохраняется.
- Запуск по запросу и каждые 15–1440 минут. При истечении авторизации расписание останавливается. Нужна повторная передача сессии.
- Удаление сессии отменяет очередь и запрещает публикацию результата уже выполняющегося задания.

Это прототип серверного сборщика, а не готовый коммерческий сервис. Нет биллинга, браузерного входа/2FA на сервере, интерфейса CRM, масштабирования, управления рекламой и SLA. Один процесс и один том на сервер. Не запускайте две реплики с одним хранилищем. Процессы Chromium изолированы по контекстам, но для публичного SaaS потребуется изоляция процессов/сети, блокировка доступа к внутренним адресам на уровне инфраструктуры, лимиты клиентов и аудит доступа. Пароль Facebook не запрашивается. Прокси не гарантирует принятие сессии Meta; checkpoint требует участия владельца.

## Развёртывание на отдельном сервере

Требуется Linux VPS с Docker Compose, домен с A-записью на сервер и открытые 80/443. Начальный ориентир для одного одновременного Chromium — 2 CPU / 4 GB RAM; это не измеренная ёмкость для большого числа клиентов.

Из корня репозитория ветки `claude-code`:

```sh
cd server
node init-config.mjs collector.example.com
# Вместо collector.example.com укажите свой домен. Создаётся .env (0600).
docker compose up -d --build
# Персональный ключ создаётся в зашифрованном хранилище.
# Provision запускайте при остановленном сервисе, чтобы не было двух писателей.
docker compose stop collector
docker compose run --rm collector node server/provision.mjs > client-key.json
chmod 600 client-key.json
docker compose start collector
curl https://collector.example.com/health
```

`client-key.json` содержит персональный `js_srv_…` ключ. Передайте его владельцу через свой защищённый кабинет, не через публичные логи. Демо-ключ расширения не даёт доступ к серверу. `.env`, `client-key.json` и Docker volume необходимо резервировать отдельно; потеря VAULT_KEY означает потерю доступа к зашифрованным сессиям. Для удаления одного клиента пока используйте собственный административный процесс; HTTP API не выдаёт новые ключи.

## Проверка с закрытым браузером

1. Обновить расширение до 0.6.0, подключить соц в Ads Manager обычной кнопкой.
2. Раскрыть «Автономный сервер», ввести HTTPS-домен и персональный серверный ключ. При необходимости задать тот же прокси, который использует профиль. Расширение не извлекает настройки прокси из Dolphin автоматически.
3. Отметить согласие, нажать «Передать подключение». Это означает только сохранение подключения, не успешный сбор.
4. Нажать «Собрать на сервере». Проверить `/v1/status`: задание должно стать `done`, результат — `source: facebook-server`, `complete: true`.
5. Включить «Каждые 15 минут», полностью закрыть локальный браузер. Не останавливать VPS.
6. После следующего запуска проверить серверный результат. `startedAt` и `observedAt` должны быть позже закрытия браузера. Сравнить ID кабинетов, числа объектов и spend с предыдущим проверенным экспортом. Только это подтверждает живую автономность.

Можно запустить сбор без расширения из CRM или отдельного терминала:

```sh
curl -H "Authorization: Bearer $JS_CONTROL_KEY" -H 'Content-Type: application/json' \
  -d '{"userId":"FB_USER_ID","since":"2026-10-01","until":"2026-10-01"}' \
  https://collector.example.com/v1/jobs
curl -H "Authorization: Bearer $JS_CONTROL_KEY" https://collector.example.com/v1/status
```

Подставьте реальный ID. Даты включительны, максимум 31 день. Расписание собирает текущую календарную дату UTC; для кабинетов в другом часовом поясе CRM должна задавать нужный период через jobs API. Сервер не пишет Telegram и не меняет рекламу.

## API

Все `/v1/*` требуют `Authorization: Bearer js_srv_…`. JSON тела ограничены 256 KB; ответы не содержат токенов/cookies/прокси/ключей. HTTPS обязателен для расширения. HTTP процесса доступен только внутри Docker и через localhost; Caddy предоставляет TLS.

| Метод | Путь | Назначение |
|---|---|---|
| GET | /health | Проверка процесса; не подтверждает Facebook |
| POST | /v1/connections | Сохранить сессию; ещё unverified |
| DELETE | /v1/connections | Удалить сессию и результат |
| POST | /v1/jobs | Поставить сбор userId, since, until в очередь |
| GET | /v1/status | Список подключений, задания, полные результаты |
| POST | /v1/schedule | userId, minutes: 15–1440; 0 отключает |

## Верификация

`node --test server/tests/*.test.mjs extension/tests/*.test.mjs` проверяет независимость очереди от HTTP клиента, восстановление после перезапуска, шифрование, принадлежность cookies, изоляцию клиентов и сохранение прошлых данных. Имитационные ответы явно имеют `source: simulation`; такой тест не подтверждает живую работу Facebook. Симулятор не принимает реальные сессии.

Живое подключение FB 0.6.0 и размещение на постоянном сервере ещё не подтверждены. Нужны домен/сервер и явная передача сессии пользователем. На этом этапе результаты прежнего локального экспорта не выдаются за серверные.
