# Управленческий бот

Ветка `feature/admin-bot`; отдельный Worker `js-control-admin` в этом репозитории. Его не нужно сливать в main для тестирования. У него отдельный токен BotFather, нет D1 binding и прямого доступа к клиентским cookies, ключам, связкам и отчетам. Доступ к административной API ограничен отдельным ключом и списком Telegram ID на обеих сторонах. Текущий разрешенный ID: `481573572`; проверьте, что это ваш аккаунт.

## Подключение после проверки клиентской версии

1. Сначала выпустить проверенную клиентскую ветку `claude-code` по `docs/SAAS-RELEASE.md`, включая миграцию `0009_operations.sql`. Управленческий бот сам не обновляет клиентский сервис.
2. Создать **нового** бота через `/newbot` в `@BotFather`.
3. В GitHub → Settings → Secrets and variables → Actions → Secrets добавить `ADMIN_BOT_TOKEN`. Токен не публиковать в чате или коде. Существующие `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` должны позволять выпуск и управление Worker secrets.
4. В Actions → Variables добавить `ADMIN_BOT_DEPLOY=true`. Если домен отличается от `js-control-admin.kirill-kanash2013.workers.dev`, задать `ADMIN_BOT_URL` с вашим HTTPS origin.
5. Запустить workflow **Check and deploy isolated administrative bot** для `feature/admin-bot`. Если GitHub не предлагает Run workflow до появления файла в default branch, новый push в эту ветку запускает его без слияния в main.
6. Скрипт создаст общие сервисные ключи при первом запуске, сохранит существующие и установит webhook. MASTER_KEY/VAULT_KEY не изменяются. Если ключ есть только на одной стороне, скрипт остановится: требуется восстановить одинаковое значение вручную; произвольная ротация запрещена.
7. Открыть нового бота, `/start`, `/clients`, `/load`. Проверить чужой Telegram аккаунт: доступ должен быть закрыт. Если клиенты отображаются, а `/load` дает ошибку, проверить версию collector и пару OPERATIONS_KEY/COLLECTOR_OPERATIONS_KEY.

Выключение `ADMIN_BOT_DEPLOY` запрещает следующие автоматические выпуски, но не отключает уже работающего бота. Для экстренного отзыва доступа удалить административный ID или ADMIN_API_KEY у platform и webhook secret у admin; это не затрагивает клиентское шифрование.

## Функции и проверка отправки

- `/clients`, карточка клиента: подписка, число подключений, использование ресурсов и обезличенные счетчики ошибок.
- `/load`: активные задания, ожидание, число отчетов и длительности за 90 дней. Это не счет за CPU, память или простой контейнера; сверять с Cloudflare.
- `/message ID текст`: предпросмотр личного сообщения, отдельное подтверждение, доставка через клиентского бота от «Команда JS Control».
- `/broadcast текст`: предпросмотр объявления, подтверждение, очередь максимум 10 получателей за минутный tick. Отказ клиента от объявлений проверяется повторно при доставке.
- `/delivery ID`: состояния очереди. `unknown` означает неизвестный результат доставки; повторять вслепую нельзя. `completed` означает, что очередь обработана, а не что каждый получатель получил сообщение: смотреть счетчики sent/skipped/unknown.
- `/history`: последние административные отправки.

Проверить на своем тестовом клиенте: отменить предпросмотр — сообщение не придет; подтвердить один раз — придет один раз; повторить подтверждение — повторной отправки не будет. Сначала проверить личное сообщение. Объявление всем запускать только после этого и с осознанным подтверждением аудитории.

Подробный журнал остается в учетной записи клиента: Профиль → Журнал ошибок или `/errors`. Администратор видит только безопасные коды и счетчики; имена кампаний, токены и тексты исключений в мониторинг не передаются. Администратор с контролем исходного сервиса технически может изменить код, поэтому эта архитектура не обещает невозможность расшифровки оператором.
