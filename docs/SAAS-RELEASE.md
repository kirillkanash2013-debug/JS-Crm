# Безопасный выпуск SaaS

## Границы этого изменения

Клиентский бот, сборщик и административный API остаются одним репозиторием. Административный бот — отдельное приложение и выпуск. Main и живые рекламные кампании не изменяются автоматически.

Push запускает проверки. Деплой SaaS в существующие тестовые Workers разрешается только при GitHub variable `SAAS_AUTO_DEPLOY=true`. По умолчанию он выключен: нет молчаливого изменения клиентских баз при публикации ветки. Workflows этого SaaS не являются production-конфигурацией для main. Старый Google Apps Script путь не переносился.

## Совместимость и порядок выпуска

1. Прогнать все тесты, включая `REQUIRE_BROWSER=1` в CI, и сборку контейнера Docker. Проверить shared/ включен в образ.
2. Отдельное тестовое окружение должно иметь собственные D1, ключи, бота и архив. Не подставлять production bindings ради проверки. Текущие конфиги указывают на существующий тестовый бот пользователя.
3. Перед обновлением существующего сервиса сохранить D1 export и зашифрованное состояние хранилищ по политике backup. Проверить восстановление на отдельной базе; backup не равен пользовательскому архиву.
4. Применить миграцию 0009_operations.sql до загрузки новой платформы. Она только добавляет поля/таблицы. Не удалять прежние поля и master keys.
5. Включить `PAUSE_JOBS=true` у сборщика при обслуживании. Дождаться завершения текущих работ (максимальные leases — 15 минут; глобальные permits — 20 минут). Чтение архива остается доступным. Сам флаг не прерывает уже начатую запись Meta.
6. Сначала выпустить collector с GlobalAdmission и новым контейнерным образом. Новые global DO создаются миграцией v2-admission; существующие клиентские DO сохраняются.
7. Затем выпустить platform. Встроенная административная API закрыта, пока не задан ADMIN_API_KEY; мониторинг закрыт без дополнительных ключей.
8. Выключить PAUSE_JOBS. Проверить свой тестовый клиент, затем согласованную группу тестеров, затем остальных. Реальное поэтапное переключение разных версий на группу клиентов требует отдельных staging/canary bindings; этот PR не имитирует его одним общим Worker.
9. Административный бот подключается отдельным выпуском после создания в BotFather.

Никогда не вращать MASTER_KEY/VAULT_KEY как часть обычного деплоя: это сделает старые секреты недоступными. Ротация — отдельная миграция с периодом поддержки двух версий ключей.

## Откат

Сохранить ID прежних версий обоих Workers и прежний образ контейнера. При проблеме включить PAUSE_JOBS, остановить дальнейшее распространение, вернуть совместимые версии Workers и контейнера. Добавленные SQL-поля оставлять: старый код их игнорирует. Восстановление backup требует отдельного решения, потому что оно может удалить новые успешные данные/платежи. Не считать rollback кода rollback данных.

Сроки leases не дают математической гарантии для зависшей внешней операции. Просроченные изменяющие задачи становятся unverified и не повторяются вслепую; их результат проверяется отдельно.

## Нагрузка

GlobalAdmission ограничивает jobs, reports и container calls. Начальная емкость каждого пула — до восьми; одновременно один permit на клиента в пуле. Это консервативная настройка для проверки, а не измеренная производительность сервиса. Node-контейнеры используют восемь общих имен слотов, каждый запрос получает отдельные connection/контекст; права клиентов не смешиваются. Старые индивидуальные контейнеры должны уснуть при переходе.

Расписание сохраняет часовую частоту, но старт распределен в первых нескольких минутах часа. Повторные запросы сбора объединяются. Ожидание глобального разрешения не запускает новую тяжелую работу. После падения разрешение освобождается по expiry; пока диспетчер недоступен, новые задания не запускаются.

Синтетический тест 100 клиентов проверяет ограничение, FIFO и восстановление диспетчера. Он не измеряет пропускную способность Meta/Keitaro или реальную память Chromium. Отдельный нагрузочный пилот должен измерить p50/p95 ответа бота, ожидание, выполнение, долю browser fallback, холодные старты, ошибки и ограничения провайдеров. Не направлять этот тест в рекламные аккаунты без отдельного разрешения.

Метрики: успешные/ошибочные задания, максимальная/суммарная длительность, число/время контейнерных запросов, число отчетов, активные разрешения и ожидание. Время запроса не равно выставленному Cloudflare счету: idle/cold-start, CPU и фактический размер storage требуют сверки с провайдером. Подробные поля ошибок остаются в клиентском зашифрованном состоянии, административная статистика содержит только коды и счетчики.

## Данные и ограничения

Keitaro использует общий транспортный контракт, пагинацию и явное incomplete. sub_id передается до Node. При отсутствии Keitaro итоговый доход/ROI не выдумывается как ноль; смешанные валюты не объединяются. Meta day остается днем кабинета — предупреждение сообщает отличие от timezone Keitaro, но не выполняет автоматическую валютную/почасовую нормализацию.

Manual timezone сопровождается инструкцией профиля Keitaro. Автоматическая timezone конкретного клиентского сервера не была подтверждена.

Журнал клиента доступен через Профиль → Журнал ошибок или /errors. Секреты и сырые exception messages не пишутся. Отключение сохраняет финансовую историю. Полный raw archive пока отключен; R2 binding нельзя включать до шифрования, retention и процедуры полного удаления. В коде будущий object key уже разделен по namespace клиента. История существующих имен не восстанавливается задним числом.

Платежный webhook — доверенный внутренний адаптер, а не готовый Bybit/provider checkout. В нем обязательны payment ID и настроенная серверная цена; ответ не содержит ключей. По умолчанию WEB_PRICE_* отсутствуют и этот канал выключен. Stars счета сохраняют цену/получателя отдельно и проверяются на оплате. Подключение Bybit, trial/promos, команды, соглашения и ИИ — следующие продуктовые изменения; не включены скрытно в этот выпуск.

## Проверки перед main

- Все node tests и legacy npm test.
- Обязательная CI-проверка Chromium, контейнерного образа и сборки Workers.
- Сверка своих отчетов Meta/Keitaro, разных sub_id, границы суток и валют.
- Два клиента, отказ чужому campaign ID, чужому Telegram chat и admin actor.
- Повторные updates/платежи/подтверждения, ошибка Telegram при отправке и перезапуск задачи.
- Проба восстановления отдельной тестовой базы и отката совместимого выпуска.
- Нагрузочный пилот; queue counters не заменяют реальные замеры.

### Paired statistics refresh

The collector completes Facebook for all connected socials before the platform fetches Keitaro. Menus and refresh taps only read the last published pair; they do not fetch Keitaro independently. A failed/partial Facebook cycle, failed Keitaro fetch, or changed Facebook generation preserves the previous pair. The encrypted `stats_snapshots` row holds one current report per tenant, with a fenced ten-minute lease to prevent concurrent replacement. The heading shows completion time; source timestamps remain actual collection times. Migration 0011 adds storage without rewriting history or keys. After the first rollout the first paired report appears after the next successful Facebook cycle.
